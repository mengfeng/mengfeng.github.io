商品规格对不上时，Agent 该让运营核对什么？

2026-11-22
AI Agent

一盏台灯为什么会有两个高度？

商品运营想让 Agent 补齐一款折叠台灯的详情页。页面当前填的是 300 mm，供应商规格表写着 32 cm，质检确认单写着 340 mm。三条记录都带着数字，但用途不同。300 mm 是当前对外展示的原值，另外两条是待核对的资料。如果 Agent 只引用供应商规格表，给出 320 mm 的修改建议，运营可能看不到质检确认单里的分歧。

这个例子处理的是同一个 SKU、同一规格版本、同一字段下的冲突。页面应该给运营看到两份资料的原值、统一单位后的数值，以及它们为何都进入了核对范围。冲突还没确认之前，页面保留 300 mm，并停在「资料冲突，待人工复核」。若供应商资料写 32 cm、质检写 320 mm，则两条有效记录在这个字段上达成一致。运营可以把 320 mm 填进本地草稿，再继续工作。

示例中的商品、供应商资料和 Agent 候选均为固定演示数据。页面包含七个场景，可离线运行。打开 Vue 交互示例 · 下载源码

读取工具返回完整范围，候选只提交建议

假设后台提供只读工具 readSpecSnapshot(sku, revision, field)。它返回当前详情页原值、本次参与判断的全部资料和一个不可混用的快照 ID。示例用内存中的固定对象模拟工具返回。正式接入时，资料的有效状态应由后端按版本、渠道和业务时间算出来。快照 ID 应绑定这些条件和具体资料版本，供应商更新附件后需要产生新快照。若工具只返回分页内容，还要等核对范围完整后再给出「可采纳」结果。

数据 提供方 核对用途
SKU、规格版本、字段、快照 ID 规格读取工具 确定候选与当前工作对象是否一致
当前展示值 规格读取工具 呈现采纳前的原值
资料 ID、来源名、数值、单位和有效状态 规格读取工具 为归一化、冲突判断和复核提供依据
快照 ID、SKU、字段、建议毫米值和引用 ID Agent 候选 表达一次建议，由程序复核

这里特意固定字段为「组装后高度」。规格表里可能同时列出包装高度、折叠高度和组装后高度，即使商品编号一致，三个字段也不能直接相互覆盖。同理，灰色款刚好有相同的外观，也只有通过 SKU 或业务系统明确维护的共用规格关系后，才能把它的记录算入当前范围。在演示里，灰色款和旧版底座的资料可以在列表中看到，但都标为「超出当前范围」。

先独立判定冲突，再核对模型的引用

一次有效引用只证明某条资料存在，单靠它会漏掉其他有效资料。程序要遍历完整快照，先根据 SKU、规格版本、字段和状态筛选，再把 cm 换算成 mm。如果符合范围的记录为空，页面给出「缺少有效资料」。如果记录有重复 ID 或毫米值无效，程序停止采纳。有效记录出现多个不同的毫米值时，直接进入冲突状态。即便模型只引用其中一条，冲突仍然能被发现。

ts
const evidence = snapshot.facts
  .filter(fact => fact.sku === snapshot.sku && fact.revision === snapshot.revision
    && fact.field === snapshot.field && fact.state === 'active')
  .map(fact => ({ ...fact, mm: fact.unit === 'cm' ? fact.amount * 10 : fact.amount }))

// 实际代码在这里检查空集合、重复 ID 和无效毫米值。
if (new Set(evidence.map(fact => fact.mm)).size > 1) {
  return { kind: 'conflict', evidence }
}

示例把有效输入约束为能换算成正整数毫米的值，适合这里的灯具样本。处理真实资料时，应按字段维护计量单位、精度和允许误差。若一个来源写的是区间，另一个来源写的是标称值，还需要单独定义兼容规则。把这些输入统一四舍五入，可能会把确实存在的规格差异折掉。

当有效资料得出唯一数值后，才检查候选。候选跨过接口时用 unknown 接收，先检查结构，再检查快照、SKU、字段、数值和引用 ID。引用至少包含一条当前有效资料，每个 ID 都必须属于当前范围，而且不能重复。程序自己已经核对了全部范围，因此候选可以只引用一条一致的有效资料。这个顺序也让运营在模型返回格式出错时依然能看见已经确定的资料冲突。TypeScript 类型收窄

让复核界面保留三件事

第一件是详情页原值。无论当前场景是否通过，演示始终把 300 mm 放在「详情页原值」一栏。第二件是资料来源。每条记录在一个位置展示来源、编号、作用范围和原始单位。默认冲突场景能直接看到 32 cm 和 340 mm，不必先打开模型的 JSON。第三件是本地草稿。只有结果为 ready 时，才显示「填入本地草稿」。点击后可见草稿变成 320 mm，详情页原值保持 300 mm。切换场景会清空草稿，避免演示中的上一个操作混到当前场景。

Vue 用 computed() 从当前快照和候选推导判定，界面不额外维护一组可能彼此矛盾的状态标志。候选 JSON 只在展开区以文本呈现。资料名也走 Vue 模板插值，便于把展示和业务判断留在应用手里。Vue Composition API 的 TypeScript 类型推断 · Vue 模板文本转义

如果线上要让人处理冲突，复核任务可以附上 SKU、规格版本、快照 ID、两条原始记录和冲突字段。确认时由服务端再读取当前版本。若供应商刚更新资料，提示运营刷新并核对新旧差异。业务可能规定质检确认优先于供应商文件，这应当成为可解释的字段规则，由审核记录追踪所选来源。演示一律将同时有效的分歧交给人工，这可以防止示例在没有真实业务规则时擅自选边。

本地运行与验收

源码包里包含已经打包好的页面。解压后可直接打开 index.html。若需修改或复跑测试，在含 package.json 的目录执行下面的命令，再访问 http://127.0.0.1:8077/。

sh
npm ci
npm run typecheck
npm test
npm run build
python3 -m http.server 8077
  1. 在默认场景核对 32 cm 和 340 mm 两条有效资料。展开「查看模拟 Agent 候选」，可以看到它只引用了供应商规格表。页面仍提示人工复核。
  2. 切到「不同单位，数值一致」，点「填入本地草稿」。草稿应是 320 mm，旧记录和别的 SKU 不参与计算。
  3. 分别切到资料缺失、旧快照、跨 SKU 引用、换算错误和结构错误场景。页面应清空之前的草稿，并禁止采纳。

离线测试覆盖上述分支，以及重复证据 ID 和异常毫米值。它验证的是特定输入能否走到正确分支。正式接入模型后，还要独立验证模型能否从真实的表格与附件中找到正确字段、保留计量单位、引用正确版本。页面对冲突的处理依赖读取工具提供完整且可信的快照。
