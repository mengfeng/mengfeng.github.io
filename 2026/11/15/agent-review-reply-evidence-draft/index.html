差评回复别急着发：Agent 先核对订单事实，再写可审阅草稿

2026-11-15
AI Agent

一条差评，不能直接变成一条承诺

假设店铺收到一条一星评价：“包裹到手时外盒破损，商品也有划痕，怎么处理？”运营想让 Agent 帮忙起草回复。一个看似顺畅的模型可能立即写出“已为您退款”，但评价本身既不能证明订单状态，也不能证明售后规则，更不能证明退款已获批。

这篇做一个只生成待审阅草稿的前端演示：Vue 3 页面读取三份独立证据，固定模拟的模型候选提出可说的事实，确定性校验器再决定哪些句子能显示。所有评价、订单和规则都是虚构内存数据；没有真实模型调用、商家接口、客户隐私、退款或对外消息。打开静态演示可以直接切换六种情况；下载完整 Vue 3 + TypeScript 源码可在本地运行。

三份证据各管一件事

这条虚构评价编号为 REV-DEMO-08，关联演示订单 ORD-DEMO-17。评价提供客户说了什么；订单记录提供当前送达状态；售后规则只提供“可引导发起售后申请”的路径。规则并没有批准退款。界面展示每项来源 ID，方便审阅者回到原始记录核对。

来源 可支持的回复内容 不能推出的结论
review.read 致歉并承认客户反馈的问题 订单确实送达、商品一定有质量问题
order.read 这笔演示订单记录为已送达 退款获批、客户已经收到补偿
policy.read 可建议在订单页发起售后申请 退款必定成功或到账时间

三项读取彼此独立。示例用 Promise.allSettled()保留每个读取的成功或失败结果；订单查不到时，评价和规则仍能显示。结果顺序与传入任务一致，所以映射到“评价、订单、规则”时不会错位。失败结果会显式标成“记录未找到”或“读取超时”，不会悄悄补一份假数据。

界面把每份证据单独列成一行：名称、读取状态、来源 ID 和最少量的业务字段。这个布局让审阅者不用从一段流畅回复里反推 Agent 究竟查过什么。来源 ID 只是演示中的索引，不是可公开访问的真实订单链接；真实产品应按客服角色的权限提供可追溯详情，并限制敏感字段在页面和日志里的展示范围。

ts
const results = await Promise.allSettled([
  readReview(), readOrder(), readPolicy()
] as const)

演示的 collect() 用 Promise.resolve() 和 Promise.reject() 制造这几种结果，不是实际网络请求。接入真实业务时，还应分清无权限、资源不存在、限流和服务故障；这里的两种错误只是最小教学样本。

先检查关联关系，再生成有限草稿

读取成功也不能直接拼接。评价的 orderId 必须与订单记录的 id 一致；不一致时，界面停止生成草稿，不能把别人的订单状态写进这条回复。读取评价时还保存修订号。页面模拟评价更新后，会立即清空旧证据；如果一次生成仍拿着旧修订号，状态转为“stale”，要求重读。

ts
if (order.id !== review.orderId) return blocked('订单与评价不匹配')
if (review.revision !== currentRevision) return stale('评价已经更新')

这种状态由明确字段驱动，而不是靠候选文字里一句“我已经核实”。示例把工具结果写成带 kind 的联合类型：ok 才有 value，missing 和 timeout 只有错误描述。TypeScript 的类型收窄文档说明了如何根据判别字段安全地访问对应分支。真实系统还应按来源契约定义读取时间、可见范围和版本一致性；本例只演示修订号与订单关联。

在订单缺失时，草稿不会说“已送达”；在规则超时时，草稿不会建议一个尚未核实的售后路径。页面依然可以给出一段有限的致歉文字，并明确标成“证据不全”。这是一个产品决策：允许客服先看见安全的起点，但不把未知项写成已确认事实。若订单与评价不匹配，则连有限草稿也停下，避免错误关联。

还要注意异步回包顺序。客服切换场景后，上一轮读取可能才完成。示例给每次请求分配序号；一旦用户改变场景或模拟评价更新，旧序号立即失效，迟到的结果不能覆盖新页面。Vue 的 ref() 类型用法让证据与评估结果分别保持 Evidence | null、Assessment | null，清空旧状态时界面会同步回到“尚未生成”。这只是前端避免错屏的一层保护；真实服务仍要在写入前核对最新订单与评价版本。

模拟候选也必须过引用关

mockCandidate() 固定返回主张代码与来源 ID，例如“承认反馈”对应评价来源，“订单已送达”对应订单来源。它只是模拟模型响应，没有调用任何 AI 服务。verify() 根据本轮证据独立算出允许的主张与来源，并要求候选的修订号、主张数组、引用数组完全一致。缺一条引用、换一个假来源、擅自加上 refund_approved，都会被拒绝，页面不渲染候选回复。

ts
if (candidate.revision !== currentRevision ||
    !same(candidate.claims, allowedClaims) ||
    !same(candidate.sourceIds, allowedSources)) {
  return rejected('候选未通过证据核验')
}

核验通过后，页面从受控句子表合成中文回复，候选的自由文本不直接进入 DOM。Vue 模板以文本插值显示草稿与来源 ID；若以后改为手动操作 DOM，使用 textContent 设置纯文本比把未经处理的模型输出交给 innerHTML 更合适，具体行为见 MDN 的 textContent 文档。生产场景还需要防止来源 ID 被替换、证据权限越界，并由服务端再次验证，不能只相信浏览器里的校验。

在页面上把失败路径走一遍

默认选择“三份证据齐全”，点击“读取证据并生成草稿”。页面展示三项来源和“等待人工审阅”的回复。再切换“订单未找到”：只剩有限草稿，不再出现送达主张。切到“政策读取超时”：仍可说已送达，但不会建议售后路径。“订单与评价不匹配”和“评价版本变化”没有可展示草稿。选择“候选擅自承诺退款”，校验器会给出 rejected，无依据的承诺不会显示。

“模拟评价更新”按钮会增加修订号并清除旧结果；“人工已审阅”复选框只改浏览器本地状态。页面没有发送按钮。因此审阅动作并不会给客户发消息，也不会创建退款。若真实业务需要发送，应该另外设计人工确认、服务端授权、幂等写入和事后追踪，不能把这个演示的本地勾选当成上线能力。

这六个场景也对应六种客服下一步：证据齐全时人工检查措辞和事实；订单缺失时先找订单；规则超时则等待规则恢复；关联冲突要排查标识；版本变化要重新读取；候选越权承诺则直接退回。前端状态文字要帮助人做这个判断，不能只用“生成失败”抹平不同原因。

本地运行与验证边界

下载源码包后，使用 Node.js 22 或更新版本执行：

Bash
npm ci
npm run typecheck
npm test
npm run build
python3 -m http.server 8765

在浏览器打开 http://127.0.0.1:8765/。npm test 覆盖完整证据、订单缺失、规则超时、订单不匹配、旧版评价、无依据退款承诺、伪造引用和不完整候选。测试验证的是固定数据和离线校验逻辑，不是模型质量、真实客服政策、生产接口或发送流程。真实接入时，应以企业实际政策和权限为准重新设计证据契约，并让人工审阅者能看到原始记录；这里没有声称生产收益或实际客服经验。

这条链路的重点是让前端把“看到了什么”和“准备说什么”并排呈现。Agent 可以帮助写得快，但对外承诺必须由可核对的事实和授权流程决定。
