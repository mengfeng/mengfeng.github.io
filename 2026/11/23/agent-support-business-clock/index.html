客服工单快超时了吗？让 Agent 按服务时段算首响

2026-11-23
AI Agent

这张跨夜工单，用掉了多少响应时间？

一张客服工单在 17:40 建立，第二天 09:20 仍等待首次回复。从创建到统计时点经过了 940 个自然分钟。演示团队每天 09:00 上班、18:00 下班，中午还有一小时休息。按这个团队的服务时段，前一天只计 17:40–18:00，第二天只计 09:00–09:20，合计 40 分钟。首响额度是 60 个服务分钟，页面应当显示「时限内」。

运营要能回答客户为什么看起来等了一晚，工单却还没超时。仅给一个分钟数，客服需要再翻排班表。这个示例会把两段实际计入的时间一起展示。遇到午休、临时加班覆盖原班次、排班拉取不全等情况，也可以切换样本，检查数字从哪里来。工单、排班和 Agent 候选全是固定演示数据，页面可离线运行。打开 Vue 交互示例 · 下载源码

在工具契约里写清楚「覆盖到哪儿」

假设只读工具 readFirstReplyClock(ticketId) 返回一个快照，其中包含工单创建时间、服务端统计时点、时限和生效排班。示例把工单限定为等待首次回复的状态，计时区域为 [openedAt, asOf)。业务系统里，一旦收到符合规则的首响事件，就应该用已确认的事件时刻截住计时。是否算首响，需要团队定义自动回执、人工回复等事件的口径。

字段 谁负责 页面如何使用
ticketId、id 只读工具 将候选绑定到工单及本次快照
openedAt、asOf 只读工具 裁剪计时跨度，展示结论对应的时点
budgetMinutes、calendarId 只读工具 明确首响额度及排班版本
coverage、shifts 只读工具 确认排班完整范围，并提供实际服务时段
snapshotId、ticketId、elapsedMinutes、state Agent 候选 与程序独立算出的结果逐项核对

coverage 表示工具能够保证排班完整的一段时间，涵盖区间里的休息段。它和 shifts 需要来自同一版本。如果覆盖跨夜时段，工具列出的两条班次之间有空档，空档可认定为停止计时。若排班只返回到午夜，第二天就没有足够证据。此时页面显示「排班范围不足」，隐藏分钟数和是否超时的判断。完整覆盖下的零分钟有自己的展示文案，客服可以看到「本次等待区间内没有服务时段」。

演示数据在构造时使用带 +08:00 的标准日期时间字符串，再用整数毫秒参与计算。浏览器格式化时显式指定 Asia/Shanghai，团队换电脑也会看到同一套业务时刻。真实排班服务需要按团队时区展开班次，并处理节假日、临时班和夏令时。页面拿到已解析的绝对时间区间后，按同一单位计算。ECMAScript 日期时间字符串格式 · ECMA-402 DateTimeFormat 构造方法

先裁剪到工单区间，再合并班次

把每条班次和等待区间取交集。先取两个起点中较晚的一项，再取两个终点中较早的一项。起点不早于终点时没有可计入的时长。午休例子在 11:50 建单、13:15 读取快照，交集是 11:50–12:00 和 13:00–13:15，合计 25 分钟。

工具可能把普通班次和临时协作班一起返回。比如在第二天 09:00–12:00 之外，还返回 09:05–11:30。后者和普通班次的交集会在裁剪后重叠。直接累加会把 09:05–09:20 多算 15 分钟，把 40 分钟变成 55 分钟。按起点排序，再把交叠或相邻的区间合并，最后累计每个区间的长度。

ts
const clipped = shifts
  .map(shift => ({
    start: Math.max(shift.start, openedAt),
    end: Math.min(shift.end, asOf),
  }))
  .filter(segment => segment.start < segment.end)
  .sort((left, right) => left.start - right.start)

const segments: { start: number; end: number }[] = []
for (const current of clipped) {
  const last = segments.at(-1)
  if (last && current.start <= last.end) {
    last.end = Math.max(last.end, current.end)
  } else {
    segments.push(current)
  }
}

排序和合并只改处理时新建的区间，界面仍能展开查看原始排班。演示按整分钟处理样本，且保留三种状态。40 分钟是「时限内」，60 分钟是「已达时限」，75 分钟是「已超时」。如果团队规则将到达时限本身计为违约，阈值归类需要跟业务服务保持一致。实际系统若记录到秒，最好以秒做比较，在标题和明细里按统一规则展示分钟，避免四舍五入改变状态。

候选错了，计时证据仍然可用

读取工具的数据与 Agent 候选分别进入页面。候选按 unknown 接收。程序先检查有没有完整可计算的区间，再比较候选中的工单 ID、快照 ID、分钟数和状态。旧快照可能碰巧也得出 40 分钟，仍要核对来源。模型若错用自然时间返回 940 分钟，页面保留独立复算的 40 分钟，并标记候选未通过。排班覆盖不足时，程序无法复算，页面展示排班缺口。

Vue 用 computed() 从当前快照推导计时结果，从快照、候选和结果推导核验状态。切换场景会更新两项派生结果，并收起上一场景的详情。进度条只显示额度消耗比例，数字仍保留 75 分钟这样的超时结果。定时刷新可以在组件的请求逻辑里取新快照，再更新页面所依赖的数据。Vue 计算属性的使用约定

真实客服系统中，工单详情和服务窗口应该由服务端基于操作者权限和工单所属队列返回。这时 Agent 适合把结构化结果讲给客服听，比如指出工单跨过了下班与恢复服务的边界。系统对外沟通、升级或者写入审计结果时，仍需读取当前工单状态并按业务权限执行。此示例只有页面读取和展示，没有发送消息或修改工单的功能。

本地运行与验收

解压后打开 index.html 即可体验。若需修改源码，在含 package.json 的目录执行以下命令，再打开 http://127.0.0.1:8077/。

python3 -m http.server 8077
  1. 在「跨夜工单」核对两段各 20 分钟。切到「午休暂停计时」应只看到 10 分钟和 15 分钟。
  2. 切到「两份班次相互重叠」，展开原始排班核对多出的班次，确认结果仍为 40 分钟。
  3. 分别查看「刚好用完时限」和「已超过时限」，核对标题及数字。再对照「排班覆盖不足」和「整段时间都在休息」，确认后者显示 0 分钟。
  4. 切换旧快照和错用自然分钟的候选，两次都应标明候选未通过，并继续显示正确的 40 分钟。

离线测试还覆盖相邻班次、恰好发生在下班时刻的工单、非法时间和跨工单候选。它测试的是固定样本上的计算与界面分支。接入真实模型后，可以另做一组可复算的样本，统计它有没有引用当前快照，以及解释是否和实际计入的时段一致。
