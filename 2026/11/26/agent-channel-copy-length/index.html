同一句活动标题，为什么换个渠道就超限？

运营写了「春季轻盈新色今日到店」，想同时放进站内推荐卡和合作渠道的短标题。推荐卡按最多 12 个字素簇验收，这一句用掉 10 个。合作渠道按最多 24 个 UTF-8 字节验收，同一句话占 30 字节。两边都写着「长度」，但使用的单位不一样。

编辑器应该在选中渠道后马上给出当前用量，并保留原文供用户编辑。Agent 可以提出精简版本「新色今日到店」。程序需要自己确认新文案只占 18 字节，还要确保候选基于当前原文和生效规则。通过这些检查后，运营仍然可以手动对照，再决定是否替换。本例使用虚构渠道、规则和固定的模型候选，页面可以离线运行。打开 Vue 交互示例 · 下载源码

先拿到明确的渠道规则

假设只读工具 readTitleRule(channel) 返回当前渠道的字段规则。这个示例只校验一个标题字段。规则版本、计数单位和最大用量由工具提供。Agent 拿到规则后只返回建议文案与绑定信息，前端根据当前规则重新验算。

字段 来源 用途
rule.id 渠道配置工具 唯一标记渠道、规则版本和字段
unit、limit 渠道配置工具 确定哪种用量参与判断
原标题、当前选择的渠道 编辑器 展示、编辑和判断旧候选是否还能用
ruleId、source、text 模拟 Agent 候选 标记所依据的原文和规则，并提出改写

线上如果同一渠道还区分站点、语言或广告位，工具需要把这些维度带进规则身份。比如推荐卡和详情页的标题限制可能不同，哪怕两个位置当前碰巧使用相同的数字。演示直接比较原字符串。对于多字段编辑器，可以使用服务端分配的草稿版本或内容摘要来匹配候选，避免把整段原文再次带进响应。

用规则对应的单位计数

JavaScript 的 text.length 统计 UTF-16 代码单元。👩‍💻 由多个代码点连接而成，字符串长度为 5，按字素簇计数是 1，UTF-8 长度则是 11 字节。如果按任意一个单元截取，可能让连接序列中途断开。Unicode 文本分段标准提供了默认字素簇边界，Intl.Segmenter 可以按字素簇迭代，TextEncoder 则会把该字符串编码成 UTF-8。对于一个标题字段按哪种单位验收，最终以渠道给出的规则为准。Unicode UAX #29 文本分段 · ECMA-402 Intl.Segmenter · WHATWG TextEncoder

ts
const segmenter = new Intl.Segmenter('zh-CN', { granularity: 'grapheme' })
const encoder = new TextEncoder()

let graphemes = 0
for (const segment of segmenter.segment(text)) graphemes++
const utf8Bytes = encoder.encode(text).length

完整示例先探测当前环境是否支持对应计数器。某个计数器缺失时，页面显示「不可用」。如果恰好是当前渠道使用的单位，本次长度检查就会停在无法确认。使用 length 顶替会给出另一种单位的结果，容易把本该超限的内容当成合格。

页面同时呈现两种数值，便于运营理解渠道变化。比如「春季轻盈新色到店」刚好 24 字节，加上一个 ASCII 的 A 后是 25 字节。组合重音也能说明差别。预组的 é 和由 e 加组合重音组成的版本各占一个字素簇，UTF-8 长度却分别是 2 和 3 字节。如果渠道规定提交前要统一 NFC，应先在约定边界执行规范化，然后计数和发送同一份文本。本例直接计算输入值保留的字符。空格和换行参与计数，纯空白另判为无标题。

候选符合长度，还要核对它基于哪一版

前端把模型返回当作 unknown。当当前草稿已超限时，再读取候选的规则 ID、原文和改写文本。示例使用 ruleId + source 检查来源。如果运营改了一处标点，或者渠道规则从 partner:v2 更新到 partner:v3，旧候选就不会显示可用的替换按钮。通过绑定检查后，程序按同一个渠道计数器重新检查改写。候选为空、类型不符或改写后仍超限，都给出具体提示，编辑区保留当前文案。

长度合规可以用程序验证。文案有没有删掉日期或把「到店」改成「立即购买」，还需要运营阅读后确认。如果业务要求短标题包含型号或活动日期，可以在生成时提交这些必留字段，并独立核对改写有没有遗漏。本例集中演示计数和候选绑定，展示建议时把它放在原文旁边，便于对照。

把实时反馈和用户操作留在编辑器

Vue 用 v-model 绑定标题与当前渠道。输入变化时，computed() 重新计算两个数值和当前规则的检查结果。示例保留超长原文，运营可以知道具体超了多少，也可以手动修改。候选通过检查时才显示「替换当前文案」。按钮只在用户主动点击后改本地输入，焦点回到标题。实际提交渠道之前，服务端仍需采用该渠道当时生效的规则再次校验。Vue 表单输入绑定 · Vue 计算属性

若把前端和后端分到不同运行环境，还应拿同一组中文、重音、emoji、换行和临界输入做对照，尤其关注 Unicode 分段版本或提交时的转换。前端的实时提示可以尽早发现问题，最终判定仍由接收渠道的规则和实际提交内容决定。本例没有连接任何广告或投放接口。

在本地复现

解压源码包后可直接打开 index.html。要改代码和运行离线测试，在包里执行以下命令，再访问 http://127.0.0.1:8077/。

sh
npm ci
npm run typecheck
npm test
npm run build
python3 -m http.server 8077
  1. 默认标题应显示 10 个字素簇和 30 个字节。切到合作渠道后应显示 30 / 24 并给出建议。点击前编辑框保持原文，点击后应显示「新色今日到店」和 18 / 24。
  2. 切到组合字符样本，确认 Café 👩‍💻 的计数为 6 个字素簇和 18 字节。刚好 24 字节的样本应通过，再输入一个 ASCII 字符就会超限。
  3. 在超限状态下修改原文，确认旧建议失效。再切换旧规则、改写仍超限、没有建议和空白标题，查看各自提示。

这些检查验证了固定规则和演示输入之间的关系。真实模型能否保留原意、以及合作渠道是否使用同样的计数口径，需要接入后分别验证。
